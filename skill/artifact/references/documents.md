# 文章、报告与文档

做以文字为主的页面时读：报告、复盘、方案、技术文档、教程、说明、解读文章。

## 1. 选格式

- 以文字为主、版式要求不高：写 `index.md`，服务端用内置阅读主题渲染，自带目录、代码高亮、mermaid 和公式。
- 需要自定义版式、交互图表、并排对比或精细的视觉：写 `index.html`，从 `assets/templates/document.html` 起步。

## 2. 常见文档的骨架

骨架是起点，按内容增删，不要为了填满骨架而写空话。

**报告 / 复盘**
1. 标题：说清对象和时间范围，如 `2026 年第三季度登录故障复盘`
2. 导语：两三句话，给出最重要的结论和数字
3. 背景：读者需要知道的最少信息
4. 发现：按重要程度排列，每条有数据或证据
5. 原因分析（复盘）：时间线 + 根本原因
6. 结论与待决定事项：需要谁、在什么时候、决定什么
7. 附录：方法、原始数据、术语

**方案 / 提案**
1. 要解决的问题（用读者能感知的现象描述，附数据）
2. 推荐方案：一段话说清做什么、改变什么
3. 方案细节：架构图、流程、接口、数据
4. 备选方案与取舍：为什么不选它们，用对比表
5. 风险与应对、回滚办法
6. 成本与排期
7. 需要的决定

**技术文档 / 教程**
1. 这篇能帮你做成什么，需要什么前提（版本、权限、账号）
2. 步骤：编号，一步一个动作；命令放在代码块里，可以直接复制；写出预期结果
3. 验证：怎么确认做对了
4. 常见问题：现象 → 原因 → 解决
5. 参考：相关链接

**解读 / 科普文章**
1. 开头直接提出读者关心的问题
2. 用一个具体例子把问题讲清楚
3. 解释机制，配示意图
4. 回到开头的问题，给出回答
5. 延伸阅读（可选）

## 3. 标题、导语、小标题

- 标题具体到能和别的文档区分开，包含对象、范围或时间。不用“浅谈”“深度解析”“一文读懂”。
- 导语是整篇最重要的段落。读者只读这一段，也应该知道结论。
- 小标题要能单独看懂。报告和方案里，小标题尽量写成结论；参考类文档里用名词作路标。
- 结论式小标题就是一句普通的话，例如 `迁移后登录延迟降到了 300 毫秒以下`。不要写成“话题：结论”（`连接建立：合并两次等待`），更不要每个小标题都用这个格式。主标题同样不加冒号副标题。
- 超过五节的长文，在开头放目录（Markdown 入口会自动生成）。

## 4. 图表穿插

图文并茂的意思是：每一个“用图比用字更快看懂”的地方都有图，而不是在每节塞一张图。逐节问自己：

- 这一节在讲一个**机制**（数据怎么流、组件怎么协作、状态怎么变）？画示意图。
- 在讲**数字的变化或比较**？画图表。
- 在比较**多个对象的多个属性**？用表格。
- 在讲**界面或实物**？放截图或照片。
- 在讲**时间顺序**？用时间线。

一篇三千字左右的报告，通常有三到六个图表。每张图：

- 放在第一次提到它的段落附近；
- 有一句图注，说出这张图的结论，而不只是名字：`图 2：迁移后，高峰期 P99 延迟稳定在 300 毫秒以下`；
- 正文里只说图里没有的东西，不把图再用文字复述一遍。

具体画法见 `visuals.md`。

## 5. 数据与来源

- 每个关键数字写清口径：时间范围、统计对象、计算方式。
- 引用外部资料时给出处和日期，能链接就链接。
- 估算值标明是估算，并写出估算方法。
- 同一个数字全文只用一种精度和单位。

## 6. 提示框与强调

- “注意”“警告”框只给不看就会出错的内容：会丢数据的操作、不可逆的步骤、安全风险。整篇一两个。
- 加粗只给扫读时必须看到的词。

## 7. 结尾

结尾回答“读完以后做什么”：待决定的事项、下一步行动和负责人、读者现在可以去做的事。然后停下。不写重复全文的“总结”，不写展望和口号。

## 8. 冷读者测试（可选）

长文档、要发给很多人的文档，发布前可以做一次：

1. 设想三到五个读者拿到文档后最可能问的问题。
2. 如果你的环境能启动一个不带上下文的子代理，把文档和这些问题交给它，看它能否只凭文档答对；再让它指出哪里含糊、哪里默认了读者不知道的背景。
3. 根据反馈修改，再发布。

没有子代理时，自己换成读者的身份，从头读一遍，记下所有需要回头重读的地方。
